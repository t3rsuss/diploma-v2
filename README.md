# Інтелектуальна система реверс-інжинірингу структур бінарних даних

[Інструкція встановлення та запуску](docs/QUICKSTART.md).

Кваліфікаційна магістерська робота за спеціальністю
122 «Комп'ютерні науки», ІСЗЗІ КПІ ім. Ігоря Сікорського.

## Основна задача

Відновлення гіпотез структури бінарних даних невідомого формату
за кількома зразками та спостереженням за програмою, яка їх читає.

Алгоритму відновлення не передається готова схема формату.
Доступний читач обробляє зразки через інструментований файловий об'єкт.
Система записує позиції, розміри й контексти читань та шукає
закономірності між файлами.

Результат — кандидати меж і ролей полів: константи, змінні поля,
довжини, лічильники, типи записів, CRC-32 та блоки даних.
Для правил довжин доступне окреме пояснення числових збігів.

## Межі реалізації

- Підтримуються доступні Python-читачі, що приймають файловий об'єкт.
- Довільні сторонні EXE-програми автоматично не інструментуються.
- Відновлені поля є гіпотезами й можуть бути помилковими.
- Готовий незалежний парсер невідомого формату не генерується.
- Усі придатні зразки запуску беруть участь у спільному відновленні.
- Підтримка правила не є ймовірністю правильності його семантики.

## Швидкий консольний запуск

Команди виконуються з кореня проєкту.
Для мінімального консольного сценарію:

    python -m pip install -r requirements-core.txt

Підготовка окремих демонстраційних зразків:

    python demo/prepare_demo.py

Скрипт створює data/demo_ready і не перезаписує наявну папку.
Якщо дані вже підготовлені, цей крок потрібно пропустити.

Відновлення структури та спільний звіт:

    python analyze_all.py --samples data/demo_ready/xdt3 --reader demo.xdt3:parse_file --limit 20 --out results/demo_ready_xdt3.json

Пояснення гіпотез довжин:

    python demo/explain_structure.py --samples data/demo_ready/xdt3 --reader demo.xdt3:parse_file --limit 20 --out results/explanation_ready_xdt3.json

Другий приклад із тим самим пояснювачем:

    python demo/explain_structure.py --samples data/demo_ready/cfg1 --reader demo.cfg1:parse_file --limit 40 --out results/explanation_ready_cfg1.json

Повна інструкція, встановлення в окреме середовище й обмеження:
[docs/CONSOLE_DEMO.md](docs/CONSOLE_DEMO.md).

## Приклади даних

XDT1, XDT2 і XDT3 — синтетичні формати для оцінювання відновлення.
CFG1 — синтетичний приклад застосування відновленої структури
до аналізу вмісту.

PNG, GIF, ICO, WAV, GZIP і DOCX використовувалися для дослідження
роботи з реальними форматами та наявними читачами.

Еталонні схеми й правильна розмітка використовуються оцінювачами,
а не передаються як вхід infer2.

### Відтворювані демонстраційні зразки

Папки `demo/samples_xdt3`, `demo/samples_cfg1` і файл
`demo/cfg1_labels.json` не зберігаються в репозиторії.
Їх створюють генератори `demo.xdt3` і `demo.cfg1`. Автоматизовані
тести також викликають ці генератори, тому перед запуском
експериментів `e26`, `e31` і `e35`, які читають зазначені папки,
зразки слід відновити явною командою з кореня проєкту:

```powershell
python -X utf8 -c "import analyze_all; from demo import xdt3, cfg1; xdt3.generate(n=20, seed=20261024); cfg1.generate(n_benign=20, n_mal=20, seed=20261025)"
```

27.10.2026 після виконання команди в чистій копії репозиторію
61 файл (20 зразків XDT3, 40 зразків CFG1 і файл міток)
мав ті самі SHA-256, що й файли робочої копії. Це перевірка
відтворюваності генерації, а не незалежна оцінка якості.

## Обмеження архівних читачів

Для вбудованих читачів GZIP і DOCX/ZIP встановлено ліміти
розпакованого обсягу та кількості елементів ZIP.
Сирі події читання відокремлено від нормалізованої траси ZIP.

Ліміти, правила нормалізації та результати перевірки:
[docs/ARCHIVE_LIMITS.md](docs/ARCHIVE_LIMITS.md).

## Аналіз загроз

Відновлені блоки та непрочитані ділянки перевіряються на окремі
індикатори. Це приклад використання структури, а не заміна
основної задачі її відновлення.

Рівні ризику не є антивірусними вердиктами.
Висока ентропія сама по собі не доводить загрозу.
Збіг заголовків PE/ELF не підтверджує повний виконуваний файл.

## Залежності й перевірки

`requirements-core.txt` — мінімальний набір, перевірений для
консольного сценарію XDT3 на Windows із Python 3.11.16.
Мінімальне середовище не призначене для всього набору тестів
і повного вебзастосунку.

`requirements.txt` — повний набір залежностей для вебзастосунку,
ML-компонентів і автоматизованих тестів.

Для коміту `080488f` підтверджено встановлення повного набору
в окреме середовище Python 3.11.16 на Windows, успішне виконання
`pip check`, 107 автоматизованих тестів і ручну перевірку
вебзастосунку. Це перевірка конкретної конфігурації, а не
гарантія роботи на всіх платформах або довільних вхідних даних.

### Встановлення повного середовища на Windows

Потрібні Git і Python 3.11. Команди PowerShell виконуються
з кореня отриманої копії репозиторію:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
```

Після помилки будь-якого кроку подальші команди виконувати
не слід. Активація середовища не потрібна: використовується
явний шлях до його інтерпретатора.

Версію `thrember` зафіксовано комітом у `requirements.txt`.
Це не повний lock-файл: версії всіх транзитивних залежностей
окремо не зафіксовано.

### Готові моделі EMBER2024

Для перевіреної повної конфігурації використовуються:

- `EMBER2024_ELF.model`;
- `EMBER2024_Win64.model`;
- `EMBER2024_Dot_Net.model`;
- `EMBER2024_Win32.model`;
- `EMBER2024_PE.model`.

Файли розміщуються в `data/ember_models`.
Еталонні розміри й SHA-256 наведено в
`docs/pretrained_models_manifest.json`.

Перевірений спосіб підготовки — локальне копіювання цих п'яти
файлів із подальшою перевіркою:

```powershell
.\.venv\Scripts\python.exe tools\prepare_pretrained_models.py
```

Якщо локальних моделей немає, скрипт має окремий режим
мережевого завантаження:

```powershell
.\.venv\Scripts\python.exe tools\prepare_pretrained_models.py --download
```

27.10.2026 мережеве завантаження перевірено в окремій порожній
папці: усі п'ять потрібних моделей відповідають маніфесту.
Завантажувач отримує весь upstream-набір із 14 моделей,
зокрема модель family розміром близько 459 МБ, яка цьому
сценарію не потрібна.
За наявності файлів із невідповідними контрольними сумами
скрипт відмовляється від автоматичної заміни; такі файли
потрібно перевірити окремо.

### Збереження власних моделей

Власні моделі `src/models/detector_elf.txt` і
`src/models/detector_win64.txt` надходять із репозиторію.

Для моделей TXT і JOBLIB у `src/models` атрибутом `-text`
у `.gitattributes` вимкнено перетворення переносів рядків Git.
Потрібно зберігати оригінальні байти моделей, а не примусово
перетворювати всі переноси на LF або CRLF.

Під час перевірки чистої копії було виявлено зміну байтів
TXT-моделей через перетворення переносів. Після виправлення
підтверджено збіг хешів із робочими оригіналами та успішне
завантаження обох моделей LightGBM.
